# 주가 데이터를 parquet 번들로 전환

작성일: 2026-09-13
대상: `work/_ko_stock`

## 1. 배경

주가 데이터를 종목당 CSV 한 개씩, 총 835개 파일로 저장소에 커밋해 왔다.
이 방식이 저장소를 빠르게 키우고 코드 이력을 읽기 어렵게 만들고 있다.

실측한 수치는 다음과 같다.

```
저장소 전체 blob : 12,140개 · 292.6 MB
stock_data 만    :  8,029개 · 172.5 MB   (전체의 59%)
```

`stock_data`를 건드린 커밋은 8개뿐인데 blob이 8,029개 생겼다.
CSV 834개가 갱신될 때마다 파일마다 새 blob이 통째로 쌓이기 때문이다
(834 × 8 ≈ 6,672). 파일이 각각 분리되어 있어 git의 델타 압축이
사실상 듣지 않는다.

**데이터 갱신 1회가 `.git`에 약 20MB를 영구히 더한다.**

부작용도 있다. 코드 한 줄만 바꿔도 `git add -A` 한 번에 CSV 834개가
함께 커밋되고, `git log`·`git diff`·코드 리뷰·`git blame`이 전부
데이터 변경에 묻힌다. 실제로 이 저장소에서 코드 리뷰 도구가
839개 파일(+10,587 −9,346) 규모의 diff를 읽다가 멈춘 적이 있다.

## 2. 목표와 비목표

### 목표

- 데이터 갱신 1회가 저장소에 더하는 양을 줄인다 (약 20MB → 약 4.8MB)
- 데이터 갱신으로 바뀌는 파일 수를 834개에서 1~2개로 줄여
  코드 이력과 리뷰를 읽을 수 있게 만든다
- Streamlit Cloud 콜드 스타트가 지금처럼 동작해야 한다
  (첫 접속자가 830종목 다운로드를 기다리지 않아야 한다)
- 노트북의 교육적 가치를 유지한다
  (학생이 CSV를 엑셀로 열어보는 실습이 계속 가능해야 한다)

### 비목표

- **앱 속도 개선은 목표가 아니다.** 전체 CSV 읽기는 합계 1.0초이고
  (`prepare_stock_data` 0.4초 + `compute_metrics` 0.6초),
  차트 루프에서 CSV 읽기 비중은 1.9%에 불과하다.
  속도는 이미 렌더링 캐싱으로 해결했다. 이번 작업의 이득은 부수적이다.
- **이미 쌓인 172.5MB는 줄지 않는다.** 과거 이력을 없애려면
  `git filter-repo` 같은 이력 재작성이 필요한데, 모든 커밋 해시가 바뀌어
  수강생의 기존 clone이 전부 깨진다. 강의용 저장소이므로 하지 않는다.
  앞으로의 증가만 막는다.

## 3. 데이터 모델

| 파일 | 위치 | 내용 | git |
|---|---|---|---|
| `stock_data.parquet` | `work/_ko_stock/` | 전 종목 OHLCV (KOSPI 지수 포함) | 커밋 |
| `kospi_list.parquet` | `work/_ko_stock/` | KOSPI 종목 목록 | 커밋 |
| `stock_data/*.csv` | `work/_ko_stock/stock_data/` | 노트북 실습·엑셀 열람용 로컬 캐시 | **gitignore** |

### stock_data.parquet 스키마

long 형식의 단일 표로 저장한다.

| 컬럼 | 형 | 비고 |
|---|---|---|
| `Code` | string | 6자리 종목코드. KOSPI 지수는 `"KS11"` |
| `Date` | datetime64 | 거래일 |
| `Open` `High` `Low` `Close` | int64 | 기존 CSV의 dtype을 그대로 유지 |
| `Volume` | int64 | |
| `Change` | float64 | |

- 정렬: `Code` 오름차순, 그 안에서 `Date` 오름차순
- 압축: zstd
- 보관 범위: 최근 600일 (기존과 동일)

KOSPI 지수를 별도 파일로 두지 않고 `Code == "KS11"` 행으로 합친다.
컬럼 구성이 개별 종목과 같아 표를 나눌 이유가 없다.

### kospi_list.parquet 스키마

`fdr.StockListing("KOSPI")` 결과에 기존과 같은 정규화를 적용한 것.

- `Code`를 6자리 문자열로 통일
- 끝자리가 `0`인 종목만 유지 (우선주 등 제외)

## 4. app.py 변경

데이터에 접근하는 지점은 6곳이다.

### 4.1 `load_bundle(data_version)` — 신규

```python
@st.cache_data(show_spinner=False)
def load_bundle(data_version):
    """번들을 한 번만 읽어 캐시한다."""
```

`compute_metrics`와 `render_chart`가 공유한다.
종목별 슬라이스를 빠르게 하기 위해 `Code`를 인덱스나 category로 둔다.

메모리는 331,756행 × 8컬럼 기준 약 20MB로, Cloud 한도 안에서 안전하다.

### 4.2 `data_fingerprint()`

CSV 835개를 stat 하던 것을 번들 2개 stat 으로 바꾼다.
반환 형식(md5 12자)과 용도는 그대로다.

### 4.3 `prepare_stock_data()`

가장 크게 바뀌는 함수다. 절차는 다음과 같다.

1. 종목 목록 확보 — 네트워크 실패 시 `kospi_list.parquet` 사용
2. 번들 적재 — 없으면 5장의 마이그레이션 규칙을 따른다
3. `KS11` 갱신 후 `market_date` 결정
4. 종목별로 번들의 마지막 날짜를 보고 부족분만 내려받는다
5. 내려받은 것을 병합하고 600일 컷오프를 적용한다
6. **실제로 바뀐 것이 있을 때만** 번들을 저장한다

6번이 중요하다. 내용이 같아도 파일을 다시 쓰면 수정시각이 바뀌고,
그러면 `data_fingerprint`가 매번 달라져 계산 결과 캐시가 버려진다.
현재 CSV 경로에서는 `save_if_changed`가 이 역할을 한다.
parquet은 바이트 단위 재현이 보장되지 않으므로 텍스트 비교를 쓸 수 없다.
대신 **갱신 루프에서 변경 여부를 플래그로 추적**해 저장을 결정한다.

`save_if_changed`는 CSV 경로가 사라지면 쓰이지 않으므로 함께 제거한다.

### 4.4 `load_market` / `load_stocks`

- `load_market` — 번들에서 `Code == "KS11"` 슬라이스
- `load_stocks` — `kospi_list.parquet` 읽기

### 4.5 `compute_metrics`

파일별 `read_csv` 루프를 번들 슬라이스로 바꾼다.

**반복 순서를 기존과 동일하게 유지한다.** 현재 코드는
종목 목록(`stocks`) 순서로 순회하며 결과를 append 한다.
`groupby`의 기본 정렬 순서로 바꾸면 결과 표의 행 순서가 달라진다.
최종 화면은 `BuyScore`로 정렬되므로 영향이 없지만,
동치 검증을 행 단위로 하기 위해 순서를 보존한다.

파일이 없어 건너뛰던 종목은 **번들에 없는 종목**을 건너뛰는 것으로 대응한다.

### 4.6 `render_chart`

```python
chart_df = bundle에서 code 슬라이스 → Date 인덱스, OHLCV 컬럼
```

mplfinance에 넘기는 표의 **컬럼 순서와 dtype이 CSV 경로와 같아야 한다.**
다르면 그림이 미세하게 달라질 수 있다. 검증 항목 2로 확인한다.

## 5. 마이그레이션

기존 clone이 자동으로 넘어가도록 세 갈래로 처리한다.

```
번들 있음                     → 그대로 사용
번들 없음 + stock_data/ 있음  → CSV 에서 번들을 만든다   ← 현재 사용자 상태
둘 다 없음                    → 기존처럼 전체 다운로드
```

두 번째 갈래에서 만드는 것은 두 파일 모두다.

- `stock_data/*.csv` (`KOSPI_list.csv` 제외) → `stock_data.parquet`
  - 파일명이 곧 `Code`가 된다. `KS11.csv`는 `Code == "KS11"` 로 들어간다
  - 읽지 못하는 파일은 건너뛰고 로그를 남긴다
- `stock_data/KOSPI_list.csv` → `kospi_list.parquet`
  - 목록 CSV가 없으면 이 단계는 건너뛴다.
    `prepare_stock_data`가 네트워크에서 목록을 받아 새로 만든다

이 갈래 덕분에 사용자는 별도 조치 없이 앱을 한 번 실행하면 번들이 생긴다.

저장소 쪽 조치는 두 가지다.

- `.gitignore`에 `stock_data/` 추가
- `git rm -r --cached work/_ko_stock/stock_data` 로 추적 해제

추적 해제는 **로컬 파일을 지우지 않는다.** 노트북 실습용 CSV는 그대로 남는다.

## 6. 노트북

`01_stock_download.ipynb`에 **"번들 만들기" 셀 하나만 추가**한다.
기존 셀은 수정하지 않는다.

학생의 흐름은 이렇게 된다.

1. 지금처럼 CSV를 종목별로 내려받는다 (기존 셀)
2. 필요하면 엑셀로 열어본다
3. 마지막에 번들을 만들어 앱에 넘긴다 (새 셀)

## 7. 의존성

parquet 입출력에는 pyarrow가 필요하다.
확인해 보니 **pyarrow는 streamlit의 직접 의존성**이다
(`pyarrow<25,>=7.0`). 따라서 Cloud에 이미 설치되어 있고
새로 설치할 패키지는 없다.

다만 app.py가 pyarrow를 직접 사용하게 되므로,
전이 의존성에 기대지 않도록 `requirements.txt`에 명시적으로 고정한다.

## 8. 검증

| # | 항목 | 합격 기준 |
|---|---|---|
| 1 | 지표 동치 | 번들 기반 `compute_metrics` 결과가 CSV 기반과 완전히 같을 것 (거래대금 6구간에서 `assert_frame_equal`) |
| 2 | 차트 동일성 | 대표 3종목의 PNG가 전환 전과 **바이트 단위로 같을 것** |
| 3 | 콜드 스타트 | `stock_data/`가 없는 상태에서 번들만으로 앱이 뜰 것 (Cloud 재현) |
| 4 | 지문 안정성 | 앱을 두 번 실행해도 데이터가 그대로면 `data_fingerprint`가 같을 것 |
| 5 | Python 3.13 | 깨끗한 3.13 venv에서 AppTest 통과 |
| 6 | 기존 회귀 | 테스트 8종 전부 통과 |

2번이 만족되지 않으면 원인을 규명하고, 픽셀 차이가 불가피한 경우
그 사유를 문서에 남긴 뒤 육안 동등성으로 기준을 낮춘다.
기준을 조용히 낮추지 않는다.

## 9. 위험과 대응

| 위험 | 대응 |
|---|---|
| 번들 파일 손상 시 앱 전체가 뜨지 않음 | 읽기 실패를 잡아 로그를 남기고, CSV 캐시가 있으면 거기서 복구한다 |
| 번들 저장 중 중단되어 파일이 깨짐 | 임시 파일에 쓴 뒤 원자적으로 교체한다 |
| 메모리 증가 (전체를 한 번에 적재) | 약 20MB로 Cloud 한도 안. `Code`를 category로 두어 문자열 중복을 없앤다 |
| 노트북과 앱의 형식이 갈라짐 | 앱은 번들만 읽는다. CSV는 실습용이며 앱의 입력이 아니다 (마이그레이션 시점 제외) |

## 10. 되돌리기

번들 전환을 되돌려야 하면 다음으로 충분하다.

1. `.gitignore`에서 `stock_data/` 제거
2. 번들에서 종목별 CSV를 다시 쓰는 스크립트 실행
3. app.py를 이전 커밋으로 되돌림

CSV는 로컬에 그대로 남아 있으므로 데이터 손실 없이 복구할 수 있다.
